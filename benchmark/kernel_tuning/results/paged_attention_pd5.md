Branch `kernels/paged-decode-pd4` (PD5 commits on top of the rc5 rebase 7c8e2aff). FlashInfer
0.7.0.post1 (the product pin) for every row. Harness: `benchmark/kernel_tuning/paged_attention_range_market.py`
(engine regime: consecutive layers with distinct KV, CUDA-graph replay, shuffled provider order per
round, paired round medians, 95% t-CI in log space, `ours_twin` = A/A copy of the product route).
Comparators as each framework dispatches on sm_120/121: SGLang 72730d6 = FlashInfer FA2 wrappers;
vLLM 0.31 = FlashInfer XQA for FP8-KV decode and its FA2 `varlen_fwd` for prefill. Verdicts as in
PD4: win (CI < 1), parity (CI contains 1), parity (<1%) (CI above 1, ratio <= 1.01), OPEN otherwise. Section 6 (review round 2)

## 1. What changed

| Mechanism | Where | Rows it closes |
|---|---|---|
| CuTe FP8-KV paged decode with a runtime KV-length split (`attention/_decode_fp8`) | `FP8_DECODE_CUTE` table, device dispatch | FP8 decode crossover rows (TP2 hd256 ranks B1-B4, Qwen3.5 B1/B3) on the RTX 5090 / RTX PRO 6000 |
| Padded fixed-split FlashInfer graph prefill | `PREFILL_GRAPH_SPLIT` (int C) | Q=256 B2-B4 extend rows on the RTX 5090 / RTX PRO 6000 |
| FlashInfer 64-row tile steering (same padded route) | `PREFILL_GRAPH_SPLIT` (`{"chunks", "tile"}`) | GB10 Qwen3-8B B1/Q256 and B2/Q64 |
| CuTe short-shape paged prefill (`attention/_prefill_cute`) | `PREFILL_GRAPH_CUTE` table | GB10 Qwen3-8B B3/B4 Q<=128, Qwen3.5 B3 Q<=128 |

**Device-side KV-length route switch.** A captured graph cannot change kernels with the runtime
KV length, which is why PD4's fixed FA2-or-XQA route lost one end of the KV range. The CuTe FP8
decode moves the switch into the kernel: the grid is host-static (S_max splits per request and KV
head, one wave), and each CTA derives its split count from the device CSR,
`count = clamp(ceil(L / min_chunk), 1, S_max)`, chunk = `round_up(ceil(L / count), 16)`. Short KV
runs one CTA per (request, KV head) with no merge (FA2-like latency); long KV spreads over the SMs
(XQA-like bandwidth). Splits merge cooperatively (every split CTA of a request merges a slice after
an arrival counter; counters self-reset). Tensor cores: FP16 MMA with Q converted once; K and V
stay FP8 in shared memory and are converted with `cvt.rn.f16x2.e4m3x2` after `ldmatrix` (K through
a k-slot permutation shared with Q, V through `ldmatrix.trans` plus byte permutes; the output
columns follow the permutation). Page ids are staged into shared memory with `cp.async`, so no warp
waits on a global index load in the key loop. Design studied: FlashInfer's FP8 fragment swizzles,
FlashAttention-2 register reuse; no code copied.

**Padded fixed split.** FlashInfer's graph prefill pads its grid to
`max(max_batch_size_if_split, ceil(T*g/tile) + B - 1)` and only splits KV while the split tiles fit
the occupancy bound. At Q=256, B=2-4 the plan cannot split and runs 1.1-1.4 waves. Planning with P
empty trailing requests raises the captured grid without changing any real tile, and
`fixed_split_size = ceil(pages / C)` then splits every request's KV into C chunks. Padding alone
changes nothing (measured); C=1 must not pass a fixed split (the provider's auto split is finer).
The same padding steers FlashInfer's tile: the graph tile comes from
`max_seq_len = total_rows - (B+P) + 1`, so P = T + 1 - 64/g - B selects the 64-row tile. Memory:
the bounded partial-output workspace grows to `hq * n * tile * (D+1) * 4` bytes with
`n = ceil(T*g/tile) + B + P - 1` (about 0.2-0.3 GB at the table's largest rows); `workspace_size()`
covers every activated (B, T).

**CuTe paged prefill.** FlashAttention-2 style: GQA-packed 64/128-row tiles, each warp owns 16 rows
and walks all keys, masks only the diagonal/tail tiles, one FFMA per score into exp2, page ids
staged with `cp.async`, optional runtime KV split with a vectorized merge, PDL. D=128 uses
64-row tiles (2 CTAs/SM); D=256 64x64 tiles with separate K/V rings.

## 3. Market receipts (product routes)

FP8-KV decode: Q=1, BF16 Q, e4m3 KV, k_scale = v_scale = 0.5, page 16, engine-shaped
context-wide page tables. Graph prefill: BF16, page 16, causal, uniform Q per request, KV
includes the new tokens. RTX 5090: 10 rounds x 5 reps (decode) / 8 x 5 (prefill), random 0-1 GiB
placement pad; GB10: 12 rounds x 5 reps, X925-pinned; RTX PRO 6000: 6 rounds x 5 reps.

**Why FP16 staging.** FlashInfer FA2 stores split-KV partial outputs in the output dtype
(`batch_decode.cu` / `batch_prefill.cu`: `tmp_v = GetPtrFromBaseOffset<DTypeO>(...)`, 0.7.0.post1), so
every split rounds its partial O to BF16 before the merge, and `run()` then applies v_scale
to the BF16 output (`out *= v_scale`, a second rounding). FP32 output is not a FlashInfer option
(`o_data_type=float32` raises KeyError). FP16 output keeps 3 more bits in the partials, and
|O| <= max|e4m3| = 448 before v_scale cannot overflow FP16. Probe (bf16 q, e4m3 KV, B3, KV 1727,
page 16, vs FP64): BF16 output + post-multiply RMS 7-9e-4, XQA 5.3-8.6e-4, FP16-staged 3.7-4.8e-4.
Cost: one extra kernel per call (B*Q*Hq*D*2 bytes), only on FA2 routes with FP8 KV; no receipt row
(B1-4 tables) uses such a route.

**Cost of the BF16 range rule.** Same-node RTX 5090 A/B, CuTe FP8 decode against the 005bc07f
kernel (ratio to SGLang, 3 repeats agree to 0.2%):
- Always BF16 QK: 5-13% slower at short KV.
- Per-stage branch between the two QK paths: 3-28% slower.
- Shipped design: whole-walk specialisation chosen once per CTA, plus the dense-KV variant. It is 0-6% slower, the remainder being the per-CTA exactness vote and the Q repack. The gap is largest when CTAs are short (B4, KV 512-2048).

Precision (BF16 KV; randomized rounds 74707071 and e65ce139):
- **Decode 8/1/d256 B2 and verify 8/1/d256 B2/Q16 (soft cap 50).** Our output is bitwise SGLang's (same FlashInfer FA2 kernel and plan). vLLM's flash-attn is more exact on every seed and dominates.

- FP16 staging cannot serve BF16 KV, because a BF16 V can exceed FP16's range. Closing these needs FP32 partials, which means a FlashInfer change or our own CuTe BF16 split-KV path.

Upstream issue text (to file with FlashInfer): "Split-KV partial outputs are

before `merge_states`; flash-attn keeps `oaccum` in FP32. `run(v_scale=...)` additionally scales
the BF16 output after the kernel (`out *= v_scale`, marked TODO), a second rounding. Request: FP32
partials (the workspace is already sized in floats) and v_scale folded into the epilogue; or
